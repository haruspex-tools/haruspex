# HAR1024: a description that isn't read

**Note.** Found reading the SQL. The output stands, without that description.

## What it means

A database may keep a description of a table, a view, a procedure, a column or a parameter in an extended property, set by
`sp_addextendedproperty` in a script or held by a DACPAC. A property under one of the names the config file's `descriptions`
gives (`MS_Description` by default) is read as a description and written beside the field, the parameter or the procedure it
describes
([decision 0128](../decisions/0128-a-column-s-description-reaches-the-fields-that-are-that-column.md)). This note says one was
passed over, and why:

- an argument isn't a string literal, an identifier or `NULL`, such as a variable, so its text isn't known;
- its value isn't text, such as `42`, or holds half of a UTF-16 surrogate pair alone;
- it names a table, column, procedure or parameter the source doesn't define, which the server refuses;
- it is set twice on one thing, under one name or two that differ only in case, which the server refuses the second time;
- it is updated or dropped (`sp_updateextendedproperty`, `sp_dropextendedproperty`), so which text stands depends on the order
  the scripts run, which a folder doesn't say.

## Why haruspex reports it

A description is the database's own documentation, and throwing away something known is a defect. A guessed one would be
worse: text beside a field that may not be the field's. So it is left out, and this note says so.

## What to do

Set each description once, with literal arguments, in the script that defines what it describes. A parameter's name is
written with its `@`, as the server requires. Nothing else changes: no type depends on a description.

## Example

```text
db/p2.sql:3:1: note HAR1024: The description of lib.book is set more than once, so which stands isn't known, and it has none.
```
