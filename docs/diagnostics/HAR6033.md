# HAR6033: a change no one function bridges

**Error.** Found by `haruspex generate` with a baseline, and by `haruspex check` with one (unless `--fit-only`). The module is
still written for every other procedure, and the run fails with exit code 1.

## What it means

With a baseline, haruspex writes types that work against both databases: the baseline, before the change is deployed, and the
source, after. A procedure changed in a way no one function can bridge in a single call: it gained a parameter without a
default, which the baseline's procedure doesn't take; it lost one that the baseline's procedure requires; a parameter's type
changed to one with no value in common with the old; a result set changed from rows to JSON or back; or a query file's text
changed since an IR baseline, which doesn't say what the new text returns from the old database. The module leaves out the
procedure's function and types, since none would work against both.

## Why haruspex reports it

A function written for the new procedure alone would fail against the old database until the change is deployed, which is the
failure combined types exist to prevent. Leaving the procedure out, and saying so, keeps every other procedure's types usable.

## What to do

Ship the change in two releases. For a new parameter, give it a default first, so that a call without it works against both
databases, and remove the default once the baseline has moved on. For a parameter to be removed, give the old procedure's a
default first. For a query file whose text changed, give the baseline as a source (a `.dacpac`, a `.sqlproj` or a folder),
which is read with the text as it is now.

## Example

```text
db/p1.sql:1:1: error HAR6033: lib.get_book parameters["@shelf"]: gained the required parameter @shelf, which the baseline's procedure doesn't take: give it a default first, or ship the change in two releases. Until then the module leaves out its function and types, since none works against both databases.
```
