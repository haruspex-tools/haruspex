# HAR2023: a SQLCMD variable a deployment replaces

**Note.** Found inferring the results. The run goes ahead; a note never changes whether it succeeds.

## What it means

A literal or a name in a body holds a SQLCMD variable, such as `'$(Region)'` or `[$(Label)]`, which a deployment (SqlPackage
publishing a DACPAC, or sqlcmd running a script) replaces with the variable's value before SQL Server sees the text. The value
may be empty or of any length, and one holding a quotation mark ends the string, so neither the written text's length, nor its
value, nor even its type holds. The value, or the result whose keys a name gives, is unknown in the output, with this reason,
and the generated schema accepts anything there. A variable that the script itself sets with `:setvar` is replaced before
haruspex reads it, so it isn't one of these.

## Why haruspex reports it

The output never claims more than SQL Server guarantees: what haruspex can't prove, it says it doesn't know, so the
output stays true. Only the deployment knows a variable's value, so a claim drawn from the text as written would be about
a procedure no server runs. The note says where, so that an unknown is never silent.

## What to do

If the value is fixed, write it in place of the variable. If it varies by deployment and you know what every deployment
gives, declare the field's type in the config file. Read
[decision 0046](../decisions/0046-a-sqlcmd-variable-in-a-body-is-unknown.md) for what each kind of source tells haruspex.

## Example

```text
db/p1.sql:1:34: note HAR2023: lib.p results[0][].region: The literal '$(Region)' holds the SQLCMD variable $(Region), which a deployment replaces with its value, so its length, value and type are not the text's.
```
