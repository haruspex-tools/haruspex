# HAR5008: a key Zod can't check

**Error.** Found emitting the Zod module. It stops the run: nothing is written.

## What it means

A result's field, a parameter or a table type's column is named `__proto__`. Written as the key of an object literal, that name
sets the object's prototype rather than adding a key. Written as a computed key, `["__proto__"]`, it is a key of the schema's
shape, but Zod skips a declared key of this name: it checks nothing there and leaves the key out of what it returns. So no
schema holds the claim the IR makes for that key.

## Why haruspex reports it

SQL Server writes the key, in `FOR JSON` and in `json_object`, and `JSON.parse` makes it a key like any other, so the IR claims
it. A module that left it out, or wrote it in a form Zod skips, would describe a value the application never gets: a type that
says the key is there, over a parsed value that lacks it ([decision 0092](../decisions/0092-a-key-named-proto-is-refused-by-the-typescript-emitters.md)).

## What to do

Name the column, alias or `json_object` key otherwise in the SQL (`AS proto`), or rename the parameter, and generate again.

## Example

```text
haruspex: error HAR5008: The type Row, which s.p returns, has a key named __proto__, which Zod never checks and an object literal can't hold; name it otherwise in the SQL.
```

**See also:** [HAR5007](HAR5007.md), the same for a result set's name.
