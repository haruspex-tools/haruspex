# HAR6014: what the module claims would change

**Error.** Found by `haruspex check`, comparing with the files in the output folder. The check fails, with exit code 1, and nothing is
written.

## What it means

What haruspex infers from the project now differs from what the IR in the output folder claims: one error for each change, at the
procedure it is in, naming the place (`results[0][].note`) and how it changed: a field added or removed, a value that became
nullable or non-null, a type that changed, a value set that grew or shrank, a procedure added or removed, a result set whose
rows changed from at most one to many.

## Why haruspex reports it

The committed module is what applications compile against. A change to the database that changes what a procedure returns
should fail the build before it is deployed, said in terms of what changed rather than as a diff of two files. Only claims
are compared: a location, the reason a value may be null, or a DACPAC's hash isn't a claim, so moving a procedure down its
file passes.

## What to do

If the change is meant, run `haruspex generate` and commit what it writes, so that the applications see it when they next
build. If not, change the SQL back. A change that only narrows what a reader receives, such as a field that became non-null,
fails too: the module changes either way.

## Example

```text
db/p1.sql:1:1: error HAR6014: lib.get_book results[0][].note: removed (string, nvarchar(200), nullable)
```
