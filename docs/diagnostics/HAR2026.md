# HAR2026: a result set returned as FOR XML

**Note.** Found inferring the results. The run goes ahead; a note never changes whether it succeeds.

## What it means

A procedure or a query file returns a result set as `FOR XML` (`RAW`, `AUTO`, `PATH` or `EXPLICIT`). The mssql driver joins the
rows SQL Server splits it into and hands the application one string, which it never parses, in either `parseJSON` mode, so the
application must parse the XML itself. That text isn't typed, and the result set is unknown, with a note of its own
([HAR2004](HAR2004.md)). A `FOR XML` subquery, such as `(SELECT … FOR XML PATH(''))` joining strings, builds a value inside
another query, not a result set, and has no note.

## Why haruspex reports it

`FOR JSON` builds the same data, rows as objects and nested queries as arrays, which the driver can parse and haruspex types
exactly, its nulls and nesting included. The note is an inventory of results that would be typed if they were built as JSON
([decision 0133](../decisions/0133-an-xml-value-is-a-kind-of-its-own-a-branded-string.md)).

## What to do

Where the application can take JSON, write the query with `FOR JSON PATH` (or `AUTO`) in place of `FOR XML`, and read it as the
README's section on JSON results says. Where XML is what the application needs, the note only says where it is.

## Example

```text
db/p1.sql:1:58: note HAR2026: FOR XML PATH('book'), ROOT('books') returns its rows as XML, which the mssql driver joins into one string it doesn't parse, so the application must parse it itself and haruspex doesn't type it; FOR JSON PATH builds the same data as JSON, which haruspex types exactly.
```

**See also:** [HAR2025](HAR2025.md), for JSON built as text.
