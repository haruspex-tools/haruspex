# Five minutes with AdventureWorks

From a fresh clone to a Zod schema for one of AdventureWorks' stored procedures, and a script that parses rows with it. The
repository keeps a copy of Microsoft's AdventureWorks install script in [`tests/corpus`](../tests/corpus/README.md), so this
needs no database and no credentials. The only downloads are the clone, haruspex's own packages from NuGet, which the first
build fetches, and zod. A test (`QuickStartTests`) runs these steps as
written, so what this page shows is what haruspex does today.

You need git, the [.NET 10 SDK](https://dotnet.microsoft.com/download) and, for the last step, Node.js 22.18 or later, which
runs TypeScript without a build step.

## Generate the module

```sh haruspex-start generate
git clone https://github.com/sharpblue/haruspex.git
cd haruspex
dotnet run --project src/Haruspex.Cli -- generate tests/corpus/sql-server-samples/samples/databases/adventure-works/oltp-install-script --include dbo.uspGetBillOfMaterials --out out
```

No package of haruspex is published yet, so `dotnet run` restores its packages and builds it first, which takes a few
minutes the first time and seconds after that. Then it reads every
`.sql` file in the folder (here one, `instawdb.sql`), infers the procedure `--include` names, and writes two files to `out`,
a folder git ignores: `out/haruspex.ir.json`, the IR, which records what haruspex inferred and why; and `out/haruspex.zod.ts`,
the module an application imports. It prints one line saying so.

## Read what it wrote

`dbo.uspGetBillOfMaterials` walks a bill of materials with a recursive common table expression and returns one row per
component. This is the module:

```ts haruspex-start module
// Generated by haruspex from IR 0.21. Do not edit.
// Rowset results follow the default type mapping of the mssql (tedious) driver.
//
// The notes on properties below rest on these facts:
// - The mssql driver builds a decimal or money of more than 15 digits as a double, which may land just past the type's
//   bounds.
import { z } from 'zod'

export const UspGetBillOfMaterialsRowSchema = z.object({
  ProductAssemblyID: z.int32(),
  ComponentID: z.int32(),
  ComponentDesc: z.string().max(50),
  /** The driver may round decimal(38,2) past its bounds in a row, so they are not checked. */
  TotalQuantity: z.number().multipleOf(1e-2),
  /** The driver may round money past its bounds in a row, so they are not checked. */
  StandardCost: z.number().multipleOf(1e-4),
  /** The driver may round money past its bounds in a row, so they are not checked. */
  ListPrice: z.number().multipleOf(1e-4),
  BOMLevel: z.int().min(-32768).max(32767),
  RecursionLevel: z.int32().nullable(),
})
export type UspGetBillOfMaterialsRow = z.infer<typeof UspGetBillOfMaterialsRowSchema>

/** dbo.uspGetBillOfMaterials: returns rows. */
export const UspGetBillOfMaterialsSchema = z.array(UspGetBillOfMaterialsRowSchema)
export type UspGetBillOfMaterials = z.infer<typeof UspGetBillOfMaterialsSchema>
```

Each line has its reason in the SQL:

- **`ProductAssemblyID` is never null**, although the column allows NULL. Every row the procedure returns passed a
  comparison of that column with a value (`= @StartProductID`, or `= cte.[ComponentID]` in the recursive step), and a
  comparison with NULL is never true.
- **`ComponentDesc` is at most 50 characters**, from the sample's alias type `Name`, which is `nvarchar(50)`.
- **`TotalQuantity`** is a `SUM` of a `decimal(8,2)` column, and **`StandardCost` and `ListPrice`** are `money` columns. The
  driver delivers all three as JavaScript numbers, so only their decimal places are checked; the note in the module's header
  says why their bounds aren't.
- **`BOMLevel` is a `smallint`**, so it stays within that type's range.
- **`RecursionLevel` may be null.** The recursive step adds 1 to it, and whether an `int` overflow is an error or NULL depends
  on `SET` options of the session that calls the procedure, which the source doesn't show. The IR says so: the value's
  `nullableBecause` is `arithmetic-overflow`. Declare what your callers set, in
  [`session`](configuration.md#the-callers-session-session), and it is typed as never null.

## Parse rows with it

There is no database here to call, so the script below makes up two rows in the form the mssql driver delivers them, and one
that the procedure can't return. In the folder haruspex wrote:

```sh
cd out
npm install zod@4.6.7
npm pkg set type=module
```

Save this as `check.ts` beside the module:

```ts haruspex-start check.ts
import { z } from 'zod'
import { UspGetBillOfMaterialsSchema } from './haruspex.zod.ts'

// Two rows as the mssql driver delivers them. The values are made up.
const derailleur = { ProductAssemblyID: 800, ComponentID: 518, ComponentDesc: 'Front derailleur', TotalQuantity: 1, StandardCost: 40.62, ListPrice: 91.49, BOMLevel: 1, RecursionLevel: 0 }
const cage = { ProductAssemblyID: 518, ComponentID: 324, ComponentDesc: 'Cage', TotalQuantity: 2, StandardCost: 0, ListPrice: 0, BOMLevel: 2, RecursionLevel: 1 }

// parse returns the rows typed, so part.ComponentDesc is a string and part.BOMLevel a number.
for (const part of UspGetBillOfMaterialsSchema.parse([derailleur, cage]))
  console.log(`${'  '.repeat(part.BOMLevel - 1)}${part.ComponentDesc} x ${part.TotalQuantity}`)

// A row the procedure can't return: a component with no name, at a level past smallint's range.
const wrong = UspGetBillOfMaterialsSchema.safeParse([{ ...cage, ComponentDesc: null, BOMLevel: 40000 }])
if (!wrong.success) console.log(z.prettifyError(wrong.error))
```

```sh
node check.ts
```

It prints the two rows as a tree, then why the third was refused:

```text haruspex-start output
Front derailleur x 1
  Cage x 2
✖ Invalid input: expected string, received null
  → at [0].ComponentDesc
✖ Too big: expected number to be <=32767
  → at [0].BOMLevel
```

An application parses each result this way before using it, so that data which breaks a claim fails at the boundary, loudly,
rather than somewhere deep in the code.
